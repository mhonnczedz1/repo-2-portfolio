Multi-Tenant RAG Documents API

A question-answering service where separate teams upload their own documents and query only their own.

What is it?Fully self-hosted: chunking, embedding, retrieval and generation all run on the host, so tenant documents never leave the machine.

Problem

Teams sit on piles of internal documents they cannot search by meaning, and pasting them into a hosted chat tool moves private material off-premise. Most retrieval examples assume one corpus and one user, so two teams sharing an instance would read each other's files.

Architecture

/ingest takes a document and a namespace, splits the text into overlapping chunks so a passage spanning a boundary stays retrievable, embeds each chunk with a local Ollama model, and writes the vectors into ChromaDB scoped to that namespace. /ask embeds the question, retrieves the closest chunks within a single namespace, and hands them plus the session's recent turns to the local generation model.

Namespace is required on both paths, so a cross-tenant read is not a permission check that can be misconfigured; it is a query that cannot be expressed. Chunking and retrieval are deterministic Python and the model is called only twice, to embed and to answer, so a wrong answer stays traceable to the chunks it cited.

Decisions and tradeoffs

  • Namespaces over a collection per tenant: one warm index instead of many, and isolation becomes a property of the query rather than a setting someone can get wrong.
  • Local Ollama over a hosted model API: no per-token cost and no document leaves the host, accepting slower generation and manual model management.
  • Overlapping chunks over clean splits: duplicated tokens in the index, but answers stop being cut off at paragraph boundaries.
  • Per-session retention over a conversation store: follow-ups work with no schema to maintain, at the cost of losing history on restart.

Impact

Stateless retrieval endpoints became a usable conversation: upload over HTTP, then ask follow-ups in the bundled interface without restating context. The isolation model is the reusable part, the problem row-level security solves in a relational database, handled at the vector layer and skipped by most retrieval examples.
